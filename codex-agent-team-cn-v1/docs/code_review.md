# Code Review 规则（偏毒舌版）

## Blocking：出现就不该过

### 1. fallback 逻辑问题
以下情况默认视为阻塞项：
- 用默认值 / 空结果 / no-op 掩盖真实错误
- 无法说明触发条件的 fallback 分支
- catch-all `except` / `catch` 后仅打印日志继续跑
- “兼容旧逻辑”但仓库里没有对应调用路径或迁移计划
- 解析失败后退回宽松逻辑，导致错误输入被吞掉
- default branch 实际上在当前 invariant 下不可能发生，却还保留并参与主路径

### 2. dead code / deletable code
以下情况至少要作为高置信候选报出：
- 本次 diff 引入但没有调用路径的 helper / method / adapter
- unreachable branch
- 永远为 true / false 的特性开关
- 已经被替代但还留着的旧接口包裹层
- 只为“以后也许要用”而保留的结构或字段
- 仅为了兜底而增加、但没有测试和真实场景支撑的代码

### 3. 测试问题
- 行为变了但单测没跟
- 新增单测了，但没有把关键断言映射到 `client/` 集成测试
- 集成测试只验证“有返回”，不验证关键业务语义
- 线上/远端接口的失败路径没有最小覆盖

### 4. 结构问题
- 为单一场景提前抽象
- 用层层委托掩盖真实 ownership
- 把不确定性塞进接口签名，却没有清晰的调用方契约
- 明显应该失败的场景却被“容错逻辑”悄悄放过

## 强简化建议：不一定阻塞，但优先删
- 删掉没有明确消费者的中间层
- 合并只用一次的 helper
- 把“防御性分支”改成显式 invariant + 明确失败
- 把模糊 fallback 改成可观测错误
- 删掉注释掉的旧代码、过时 TODO、遗留调试分支

## 输出格式
1. Blocking findings
2. 高置信 dead code / deletable code
3. 强简化建议
4. 可选 nits

## 证据要求
- 不要只说“感觉复杂”
- 要指出具体文件、具体分支、为什么可能不会被触发、或者为什么会掩盖 bug
- dead code 候选至少要给一个证据：
  - 无调用路径
  - 被 invariant 排除
  - 被新实现替代
  - feature flag 常量化后不可达
