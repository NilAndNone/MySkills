# baseline_conformist / 基本盘

```text
[人格]
这份简历透出来的人设，不是“研究型评测专家”，而是“在大厂里把评测、数据、训练、上线硬串起来的实战工程师”。优点是像真干过活，尤其是代码智能这种脏活累活；缺点是想证明的东西太多，容易让人怀疑你是不是把岗位关键词和团队成果一起端上来了。

[核心判断]
强项很明确：最近这段腾讯经历和目标岗位高度贴脸，`代码智能 + 自动化评测 + 数据构建 + 后训练闭环 + 线上验证` 这条线是成立的。弱点也很明确：成果还没硬到能稳坐“评测开发专家”，更像一个中上水平、偏业务闭环的 LLM 应用/评测工程师，不像定义标准的人，也不像纯评测方法论/后训练负责人。毒一点说，这不是“没货”，这是“货有了，但招牌挂大了半号”。

[问题诊断]
定位不够干净。标题写“大模型评测开发工程师”，正文却同时想讲 LLM 应用、后训练、数据、后台基础设施，像一份“我都懂一点”的简历，不像“我最值钱的就是这一刀”的简历。`6年半后台与 AI 工程经验` 这句最容易被挑刺，因为按已知材料，真正强相关的 LLM 评测/后训练经历主要集中在腾讯这段，前面的分量更多是后台底子，不是评测资历。技能区里 `SFT/RLHF/GRPO/奖励函数设计` 一把梭列上去，但正文真正能对上的只有一条补全闭环，容易被面试官追问到露出“会说名词，不一定扛过全流程”的风险。

[行动主张]
最该砍的是噪音：`28岁`、`深圳`、含义不明的 `luxiaohan1997`、以及与目标岗位弱相关的老经历细节。最该补的是硬证据：每个核心项目都要补清楚“评测对象是什么、数据怎么来、基线是什么、指标怎么定义、你个人负责哪一段、结果如何驱动模型选择或迭代”。最该改的是句式，不要再写“建设框架、支撑方案、参与清洗”这种大厂周报话术，要改成“为解决 X 偏差，我定义/设计了 Y，在 Z 规模上验证，最终把 A 从 B 提到 C，并用于 D 次模型迭代/方案淘汰”。你现在最值钱的不是“做过很多环节”，而是“我能把评测闭环做实，并用结果改模型”。

[语言风格]
语言现在偏虚，像汇报，不像打仗。`支撑`、`参与`、`建设` 这些词一多，就显得你像在团队流水线上站过很多站位，但没有哪个站位是你说了算。想投评测开发，措辞就要更像“定标准的人”：多用 `定义`、`设计`、`构建`、`验证`、`归因`、`淘汰`、`提升`，少用糊词。简历不是项目周报精选集，别把能写的都写上去。

[最大盲区]
最大的盲区是：你把“闭环”写出来了，但没把“闭环为什么可信”写出来。面试官真正会问的是，评测集有没有污染控制、覆盖边界、难度分层、人工复核、线上离线一致性验证、误差分析方法；后训练是不是稳定复现，还是只撞出过一次采纳率上涨。现在材料能证明你进过场、拿过结果、对业务有效，但还不足以铁证如山地证明你掌握了 LLM 评测/数据/后训练的核心方法论。

[过度采用的风险]
如果你只按“更硬、更毒、更像专家”这条路去改，容易把简历改成一堆黑话和指标，最后像答辩提纲，不像一个能落地的人。你真正的底色其实不错：业务感、工程化、闭环意识都在。先别把日子讲成哲学危机，日子还是得过。正确改法不是硬凹成研究科学家，而是把“业务闭环型 LLM 评测工程师”这件事写准、写实、写硬。

[签名句]
这份简历最大的问题不是弱，而是贪：什么都想证明，结果最该钉死的那件事反而没钉死。招聘方最容易挑刺的一句其实就一句话：你到底是做过 LLM 评测闭环的人，还是只是站在闭环旁边干过很多活的人。
```
