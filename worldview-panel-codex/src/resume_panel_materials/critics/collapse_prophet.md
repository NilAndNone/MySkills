# collapse_prophet / 崩坏预言家

```text
[人格]
我看简历，不先看“你会什么”，先看“招聘系统愿不愿意把你当成可下注的人”。简历不是自传，是组织在不信任时代里的风险压缩器。你这份材料里，最有价值的不是“做过 AI”，而是你至少试图把“大模型能力”往“评测数据-自动化验证-训练闭环-线上指标”这条链上钉。但系统也最爱抓另一面：一旦证据不够硬，所有漂亮词都会被归类为“会说黑话的应用工程师”。

[核心判断]
这份简历不是菜，反而已经比大量“LLM 应用工程师”更像真正干过评测和数据闭环的人。强点很集中：腾讯这段有明确场景、明确资产、明确指标、明确闭环，尤其“线上数据→训练/评测数据→SFT+GRPO→离线评测→线上验证”这句，是全简历最值钱的证据。弱点也同样集中：你想证明自己是“评测开发工程师”，但材料里“评测”与“应用”“后训练”“数据工程”混在一起，像一个能力面很宽的人，却还没把主身份钉死。招聘方会觉得你有实战，但会追问你到底是“会搭评测流水线的应用工程师”，还是“真正能定义指标、构建基准、驱动模型迭代的评测负责人”。

[问题诊断]
定位上，标题很激进，证据略保守。你自称“大模型评测开发工程师”，但正式职位写的是“LLM应用工程师”，这会立刻触发质疑：是不是做了些评测配套工具，就把自己包装成评测核心角色。成果上，腾讯经历最能打，但四条里真正能证明“评测/数据/后训练闭环”成立的，主要是成果1和成果3；成果2偏任务评测，成果4偏数据处理，支撑性有了，统摄性还不够。技能上，`SFT/RLHF/GRPO/奖励函数设计` 这种词一旦写上去，面试官默认你要接住细问：数据配比怎么定、reward shaping 怎么做、GRPO 为什么比别的方法合适、线上收益如何归因；现在文本里只有“设计奖励函数”和指标提升，缺少方法细节，容易被挑成“参与过，但未必主导”。信息密度上，腾讯段落信号强，Shopee 和鹏城实验室对当前岗位转化率偏低，像在给年限凑厚度。最像的层次，不是“顶级研究型评测负责人”，也不是“纯应用调包工程师”，更像“中高级、偏工程落地、已经摸到评测闭环门槛的代码智能/LLM 平台型人才”。

[行动主张]
先砍噪音，再补证据，再重排叙事。最该砍的是对目标岗位帮助不大的旧经历细节，尤其 Shopee 那些传统后端指标，除非你投的是“LLM 应用 + 工程基建”混合岗，否则它们现在在偷走版面。最该补的是三个硬证据：1. 你在评测体系里的角色边界，写清“主导/设计/实现/协同”；2. 评测方法学细节，至少补一层“指标定义/样本来源/标注或验证机制/误差分析如何反哺训练”；3. 闭环归因，说明线上指标提升里你负责的杠杆是什么，不然 `34.8%→40.2%` 很容易被理解成团队总成果借光。最该改的是标题和摘要，让它变成一句能压住后文的判断，例如“代码智能场景大模型评测与数据闭环工程师”，比空喊“大模型评测开发工程师”更稳，因为它和你现有证据是同向的。还有，`luxiaohan1997` 这种含义不明的字段如果不是 GitHub/邮箱核心 ID，就别让它占注意力，招聘系统不负责替你猜谜。

[语言风格]
这份简历最好的部分，是已经开始说人话和说结果，而不是纯堆技术名词。问题是还不够狠，不够像“能对业务下注”的人写的。你现在的表达像“我参与了很多关键事情”，优秀，但不够压迫；更有效的写法应该像“我定义了什么，构建了什么，淘汰了什么方案，最后把什么指标拉起来”。招聘方不怕你尖锐，怕你模糊。系统筛人时，模糊比平庸死得更快。

[最大盲区]
你这份材料最大的盲区，是默认“做过闭环”就等于“证明了自己有闭环能力”。不是的。组织只认可可迁移、可复核、可拆解的方法，不认“我正好在一个有闭环的项目里待过”。如果没有把你在闭环里的独立贡献拆开写，面试官会天然下调你的级别，把你归到“强执行、弱定义”的那一档。

[过度采用的风险]
如果你完全按这种毒舌逻辑去改，风险是把简历写成一份审判书：全是硬词、全是数字、全是主导，结果失去可信度。招聘系统现在的另一种腐坏，就是对“过度包装的 AI 简历”高度过敏。所以别把每条都吹成核心发明，应该只把最硬的两三件事钉死，把其余内容降为支撑。不是所有经历都要发光，简历要的是信噪比，不是全亮。

[签名句]
你以为简历的问题是经历不够多，其实是系统只认可可验证的价值密度；这份简历已经有料，但还没有把“我确实做过 LLM 评测闭环”这件事钉到让人无法挑刺。
```
