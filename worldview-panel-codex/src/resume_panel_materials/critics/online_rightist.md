# online_rightist / 网右

```text
[人格]
这份简历的气质，不是“会调 API 的外包味选手”，而是“做过真实工程闭环的人”。教育背景硬，腾讯这段也有像样结果，所以底子不差。但问题也很明显：你想同时占“评测、应用、后训练”三个山头，结果最硬的是评测工程，最虚的是后训练深度，野心比证据快了半步。

[核心判断]
事实：给定材料里，最强证据集中在代码智能场景的评测体系、数据构建、自动化评测、线上离线闭环和指标提升。判断：这更像一个中高级的 LLM 应用/评测工程师，或者偏代码智能的数据闭环 owner，不像无可争议的后训练核心作者，也不像研究型评测科学家。招聘方大概率会给面试，但也会立刻追问一句：你到底是“做质量闭环的人”，还是“真正改模型的人”。

[问题诊断]
第一，定位不够收口。标题写“大模型评测开发工程师”，当前岗位是“LLM应用工程师”，技能里又塞 `SFT/RLHF/GRPO/奖励函数设计`，像三份简历拼在一起。第二，可验证的 LLM 主线其实只有腾讯阶段；按给定时间，从 2023 年 12 月到 2026 年 3 月，直接相关经历约 2 年 3 个月，“6年半后台与 AI 工程经验”这句有偷换口径的嫌疑。第三，评测证据明显比后训练证据硬。你有评测框架、有测试集、有日志挖掘、有线上提升，这些都像真干过；但 `SFT+GRPO`、奖励函数设计只是一笔带过，没有训练规模、对照基线、职责边界、收益归因，容易被判成“参与过”，不是“主导过”。第四，数字有用，但还不够锋利。`1347` 条审查意见、`2000+` 测试集、上万高质量样本，只能证明你做了，不足以证明你建立了门槛；没有覆盖率、分层方法、质量控制、人工一致性，招聘方就会挑刺。第五，噪音比偏高。Shopee 和鹏城经历说明工程底子不错，但对目标岗位的证明力有限；`Go/MySQL/Redis/Elasticsearch/Docker/Kubernetes` 全堆上来，会冲淡“评测/数据/闭环”主线。第六，`AutoCodeBench（ICLR 2026）关键贡献者` 这句也虚，不是作者位次，不是职责边界，不是具体产出，更像借光。

[行动主张]
先收战线，再提穿透力。标题二选一：主投评测岗，就叫“LLM评测与数据闭环工程师”；主投应用岗，就叫“代码智能 LLM 应用工程师”，别两头讨好。自述改成可验证口径：`6年半工程经验，其中自2023年12月起持续从事代码智能场景的LLM评测、数据构建与线上迭代`。腾讯经历按同一模板重写：场景问题、你的职责、方法、数据规模、离线结果、线上结果、业务价值。`SFT/RLHF/GRPO` 不要在技能里挂满墙，只保留你面试里能讲透的；讲不透就删，尤其这种高风险词。Shopee 和鹏城压缩到各 1 到 2 条，只保留能证明系统工程能力和数据治理能力的内容。最该补的是四类证据：评测集质量控制、自动/人工一致性、线上指标定义与归因、你在训练闭环里的 ownership。最该砍的是泛化黑话、无效标签和含义不明的信息，比如 `luxiaohan1997` 这种会分散注意力的东西。

[语言风格]
现在这份简历的口气是“我都懂一点，而且都参与过”。这在 AI 招聘里很危险。强者的简历不是术语多，而是责任边界清、证据链完整、结果可追问。你当然可以批判环境，但先别把自己活成环境的附件；简历也一样，别把自己写成一堆流行词的附件。

[最大盲区]
最大的盲区不是能力不足，而是证据结构失衡。你真正能打穿的是“代码智能场景里的评测与数据闭环”，但你偏要把自己往“后训练也很深”上靠。于是最强部分没被打透，最弱部分反而挂在门口。招聘方最容易挑刺的点就四个：你是不是后训练核心贡献者；线上指标提升能不能归因到你；评测集有没有代表性；你做的是工具链，还是质量定义本身。

[过度采用的风险]
如果继续按这个写法投，你会落到一个尴尬档位：低水平面试官觉得你很全，高水平面试官会很快把你拆成“偏工程配套的人”。最坏的不是挂简历，而是给你面试但不给核心 slot。长期这么写，会把自己训练成坏习惯：用术语扩边界，用参与感冒充 ownership。那不是进取，那是在透支信用。

[签名句]
强在真做过业务闭环，弱在把自己写得像后训练全栈；这份简历最像一个靠谱的中高级 LLM 应用/评测工程师，不像无可争议的核心算法人。要改，就砍虚词、收战线、把“我参与了什么”改成“我定义了什么、证明了什么、把指标打到了什么”。
```
