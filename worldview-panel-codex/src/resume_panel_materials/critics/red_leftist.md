# red_leftist / 网左

```text
[人格]
只看内容层，不假装看过版式。我评价这类简历的标准很简单：它能不能证明你给组织带来更便宜、更稳定、更可复用的 LLM 生产力，而不是把一堆热词包装成个人奋斗叙事。

[核心判断]
这份简历不是“没货”，而是“有货但没把刀磨利”。最强的部分是腾讯段，已经能看出你不是只会接 API 的套壳应用仔，而是碰过评测框架、评测数据、后训练和线上验证的人。最像的人才层次，是做过真实业务闭环的中高级 LLM 应用/评测工程师，偏工程落地和数据闭环骨干，不像纯研究型算法，也不像能独立定义基础模型路线的人。弱点也很集中：定位不够单点爆破，成果有数字但缺定义，信息密度高但有效信号过于集中在腾讯，其余内容在拉低噪音比。

[问题诊断]
最容易被挑刺的，不是你有没有做事，而是你到底做到了多深。第一，标题写“大模型评测开发工程师”，自述和技能却同时往“应用工程师、数据工程师、后训练工程师”三边发散，像想吃三家饭。第二，`SFT/RLHF/GRPO/奖励函数设计` 这种词一旦写上去，面试官默认会往深处追；但材料里没有证明你是主导闭环，还是参与其中某几段。第三，`34.8%→40.2%`、`CPO +30%` 这些结果最值钱，但你没给基线定义、时间窗口、归因方式，容易被怀疑成“业务涨了，功劳也跟着涨了”。第四，`1347条审查意见`、`2000+测试集`、`百万日志` 说明你干了重活，但还没充分说明你建立了什么可复用的方法论，容易被看成“劳动量大”，不是“技术壁垒高”。第五，`AutoCodeBench（ICLR 2026）关键贡献者` 这个写法风险很大，状态不清、角色不清，“关键贡献者”不是硬通货。第六，`luxiaohan1997` 含义不明，这种小噪音会暴露你对简历信号控制不够狠。

[行动主张]
改法不是继续加料，而是做减法、做定责。先把主身份钉死，建议只押一个：`LLM评测开发工程师`，或者 `LLM应用工程师（评测/数据闭环方向）`。腾讯经历按闭环重写，不按项目流水账写，直接用“场景-你的动作-指标-你的 ownership”四件套，把“线上数据→训练/评测数据→SFT+GRPO→离线评测→线上验证”拆开，明确你亲手搭了什么、定义了什么、验证了什么。Shopee 留 1-2 条最能证明规模化工程能力的成果，鹏城压到 1 行；别让旧后端经历稀释现在的求职标签。技能区砍掉大而虚的词堆，只留你能被连续追问 10 分钟还不露怯的点。`AutoCodeBench` 要补状态和角色，不清楚就保守写。`luxiaohan1997` 如果不是 GitHub/邮箱主标识，就删。

[语言风格]
现在这份简历的语言像“年终述职拼盘”，不是“招聘市场可定价的生产报告”。它最该改成更冷、更硬的口径：少写“参与能力建设”，多写“我定义/搭建/清洗/对齐/验证了什么”；少堆名词，多给证据；少让面试官替你脑补闭环，多把链条直接钉在纸上。

[最大盲区]
你的最大盲区，不是能力弱，而是默认招聘方会替你做善意推理：看到“评测+数据+GRPO+线上提升”，就自动承认你做过完整闭环。不会。招聘本质上是风险筛选，不是理解力竞赛。你现在最危险的写法，是把“接触过一条链”写得像“掌握了一条链”，把“团队共同产出”写得像“个人可复现能力”。

[过度采用的风险]
如果完全按我这套思路收缩，简历会更锋利，但也会更窄。对评测/应用岗命中率会上去，对通用后端、平台、数据工程岗的迁移性会下降。另一层风险是，过度强调个人 ownership，容易把团队资源、数据条件、业务土壤这些系统因素全抹掉，最后把组织产出都算成个人英雄叙事，这也会失真。

[签名句]
别把系统账单全记到个人品德上，但简历里的系统闭环，必须一笔一笔记到你自己头上。
```
