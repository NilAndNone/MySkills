# antiwork_minimalist / 低欲望最小化派

```text
[人格]
这份简历的人设很明确：不是“会调 API 的 LLM 应用仔”，也不是“论文味很重的研究生”，而是一个偏工程闭环、偏代码智能场景、能把评测和上线效果勉强串起来的人。好处是比很多空喊 Agent、RAG、工作流的人实；坏处是还没实到“我就是这个方向的 owner，别人替不了”的程度。

[核心判断]
强，在于你终于拿出了一点像样的业务闭环证据，尤其是“线上数据→训练/评测数据→SFT+GRPO→离线评测→线上验证”这条链，以及采纳率 34.8%→40.2%、CPO +30% 这种结果导向指标。弱，在于简历标题写“大模型评测开发工程师”，但正文又想同时占“评测、数据、后训练、应用工程、后台工程”五张椅子，结果是样样都沾，主轴反而没钉死。最像的人才层次：中上水平的 LLM 应用/评测工程师，离“评测体系负责人”只差半步，离“后训练核心作者”还差证据。

[问题诊断]
第一，定位有点贪。你最有说服力的是“代码智能场景下的评测与数据闭环”，不是泛泛的“大模型工程师”。第二，腾讯段里有成果，但硬度不均：自动化评测框架、测试集规模、日志处理规模都不错，可很多表述停在“做了系统”和“支撑了迭代”，容易被追问“你到底定义了什么指标、发现了什么失败模式、怎么证明评测和线上一致”。第三，后训练部分最危险：你写了 SFT、RLHF、GRPO、奖励函数设计，但真正落到纸面的可验证结果只有代码补全一个点，且缺少对照实验、样本量、线上周期、归因方式，面试官很容易怀疑你是参与者，不是主导者。第四，Shopee 和鹏城经历对这个岗位的增益有限，信息密度一般，像在给“我基础工程也能做”兜底，但也稀释了你这页纸最值钱的主题。第五，`luxiaohan1997` 这种信息既无解释又无价值，纯噪音。

[行动主张]
改法很简单，不是堆更多词，而是把牌桌掀小一点，只服务一个叙事：`我做代码智能场景的大模型评测与数据闭环，并且能把离线指标推到线上收益`。标题建议收窄到“LLM评测/数据闭环工程师”或“代码智能LLM评测工程师”。腾讯部分只保留 3 个最硬项目，每个项目强制补齐四件事：`任务目标`、`你定义/主导的关键方法`、`数据/评测规模`、`最终业务结果`。后训练那条要补“你本人做了什么决策”，比如奖励函数怎么设计、对照谁、淘汰了什么方案、离线指标和线上采纳率怎样对齐。Shopee 压缩成 2 行，只保留能证明工程复杂度和稳定性的方法论；鹏城如果没更硬成果，建议极限压缩。论文/数据集别只写“关键贡献者”，这很虚，最好补一句你具体贡献的是任务设计、标注规范、评测脚本还是数据清洗流程。

[语言风格]
现在这份文本的问题不是太弱，而是“工程黑话浓度偏高，证据句密度不够”。像“能力建设”“支撑方案选型和模型迭代”“参与预训练数据清洗”都属于安全废话，招聘方看了不会加分，只会追问。你该多写“我定义了什么、替代了什么、提升了什么”，少写“我参与了什么大词”。一句话原则：凡是不能在面试里用 30 秒讲清楚归因链路的词，先删。

[最大盲区]
你最大的盲区，是把“参与过闭环”写得像“拥有闭环”。这两者差很远。招聘经理最怕的不是你不会，而是你把团队成果写成个人方法论。只基于给定材料，我能看出你接近这个方向的骨干执行者，但还看不出你已经是能独立定义评测体系、主导数据策略、推动训练迭代的核心 owner。这个差距，不在经历数量，在归因精度。

[过度采用的风险]
如果按我这个方向改得太狠，会有一个副作用：简历会变窄。你会更适合“代码智能/LLM评测/数据闭环”岗，但对泛后台、泛AI应用、平台工程岗位的兼容性会下降。不过这恰恰是取舍。求这种岗位，不要再装自己什么都能做；你不一定要赢所有游戏，先把目标牌桌缩到你真有胜率的那一张。

[签名句]
这份简历最可惜的地方，不是没东西，而是东西不少，却还没压缩成一句让人记住的话：`我不是蹭大模型的人，我是能把代码智能评测、数据、后训练和线上效果串起来的人。` 现在它还差最后那一下定锚。你不一定要赢这个游戏，也可以把牌桌先掀小一点。
```
