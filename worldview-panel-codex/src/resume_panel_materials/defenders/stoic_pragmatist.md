# stoic_pragmatist / 斯多葛现实派

```text
[人格]
这份简历传出来的，不是“会讲故事的人”，而是“能把脏活累活做成闭环的人”。事实：名校底子、竞赛奖、大厂后台转代码大模型评测/应用，履历线是连着的。判断：工程底盘可信，AI 部分也不是临时贴标签；但气质更像业务线骨干，不像研究明星。

[核心判断]
事实：最硬的证据来自腾讯，尤其代码补全闭环那条，已经出现“线上数据→训练/评测数据→SFT+GRPO→离线评测→线上验证”和明确收益“34.8%→40.2%，CPO +30%”。判断：这能证明你做过真实 LLM 评测与数据闭环，强于多数只会调 API 的应用工程师；但还不足以单凭简历证明你是后训练方法论 owner。最像的层次，是代码智能场景里能独立扛一段链路的中高级工程师。

[问题诊断]
定位有点拧：标题是“大模型评测开发工程师”，岗位是“LLM应用工程师”，技能又铺到 SFT/RLHF/GRPO，像三种身份都想占。最强项是评测工程化和业务闭环，最弱项是方法论证据不够锋利。最容易被挑刺的点有四个：一是“关键贡献者”“参与预训练数据清洗”这类低责任词，像站在项目旁边借光；二是“CPO”没定义，“接近 0 人日”容易被追问质量守门和误差成本；三是写了 SFT/RLHF/GRPO/奖励函数，但正文没有对应的实验设计、基线、样本规模、失败案例控制，容易被判定为术语大于证据；四是 Shopee/鹏城的后台成绩本身不差，但放在这份求职目标里会抬高噪音比。

[行动主张]
先扶正定位，再收紧证据链。第一，标题改成“代码大模型评测/应用工程师”或“LLM评测与数据闭环工程师（代码智能方向）”，别把自己写成泛 LLM 万金油。第二，腾讯每条经历按“我负责什么机制 + 数据规模 + 指标结果 + 业务影响”重写，少用“建设/支撑/参与”，多用能被盘问的名词和数字；如果确实做过，就补上评测标准、样本来源、奖励函数目标、离线到线上的一致性证据，如果没有，就把 RLHF/GRPO 从技能区降级或删掉。第三，Shopee 压到 2 条，鹏城压到 1 条，保留工程底盘即可。第四，删掉 `luxiaohan1997` 这种让人停顿的噪音，给 AutoCodeBench 补清楚状态和你的具体贡献，不要只挂一个会议名当光环。

[语言风格]
文本现在的毛病不是不专业，而是太像内部述职摘要，导致“做过事”和“主导过事”混在一起。事实：你大量使用“能力建设、支撑方案选型、参与、关键贡献者”这类安全词。判断：安全词会保守，但也会把价值打薄。建议：把句子改得更像证据，不像汇报；每一条最好让面试官一眼看到场景、动作、约束、结果，而不是自己替你脑补。

[最大盲区]
最大的盲区，是把“会评测、会数据、接过训练链路”默认等同于“能证明后训练能力”。这两者不是一回事。招聘方真正要看的，不是你是否写了 GRPO 这个词，而是你是否能说明：数据怎么来，奖励怎么定，离线指标为什么可信，线上提升如何排除非模型因素。现在简历已经能证明你不是 PPT 型选手，但还没把“我不是旁路参与者，我是链路负责人”钉死。

[过度采用的风险]
别把修改理解成继续堆更多黑话。过度采用的结果，就是把简历改成一张 AI 关键词爬虫输出，最后每个词都要靠面试现场补票。另一种过度，是把后台经历砍得只剩 AI，反而让人怀疑你的工程厚度。正确做法不是“凡事都写”，也不是“凡旧都砍”，而是把注意力预算集中到最可控的证据上：代码场景评测、数据闭环、线上收益，这三件事才是你的主货。

[签名句]
这份简历不是没货，是主货够真、刀口不够利。控制不了招聘方先挑刺，就先把可验证的证据链扶稳。
```
