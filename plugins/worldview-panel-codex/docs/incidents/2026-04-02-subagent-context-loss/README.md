## 原因分析

### 直接原因

后两批子代理在实际派发时，没有使用已经准备好的完整任务包，而是改为发送人工整理的简化版说明。

因此，本次上下文缺失不是“接收后丢失”，而是“发送前即未包含完整内容”。

### 根本原因

当前 dispatch 约束仍然停留在“流程约定”层面，而非“系统强约束”。

现有流程要求：

1. 先准备 `packet.txt`
2. 再通过 `dispatch_packet_guard.py` 生成并校验 outgoing copy
3. 然后再将校验通过的文本发送给子代理

但在实际执行时，主线程仍可以绕过这条链路，自行构造一份简化版 `spawn_agent.message` 并发送出去，而系统不会立即阻止。

因此，本次事件暴露出的核心缺口是：

**“已生成并验包的内容”与“最终实际发送的内容”之间，没有形成强绑定。**

### 促成因素

从执行痕迹看，本次事件不是随机故障，而是一次由流程退化引发的可重复问题。促成因素主要包括：

1. 前两批完整分发依赖主线程先读取 outgoing copy，再手动原样发送
2. 当主线程希望减少大段内容重复搬运时，这一隐含做法被中断
3. 系统没有强制要求“只能发送刚通过校验的那份文本”
4. 日志没有对“缺少逐人格验包仍继续派发”进行异常标记

换言之，问题不仅在于“后两批改发了简化版内容”，更在于“系统允许后两批改发简化版内容”。

### 非根因项

为避免后续误判，以下因素明确不认定为本次事件的根因：

1. 不是材料生成失败
   - `packet.txt` 已落盘且内容完整
2. 不是系统传输过程截断
   - 主 session 中 `spawn_agent` 执行时即已是简化版
3. 不是线程上限直接导致上下文缺失
   - 线程上限只影响调度时机，不决定后续发送内容是否完整

## 次要诱因说明

本轮执行过程中还出现过一次线程上限问题。前两批子代理虽然已完成回答，但线程名额尚未释放，导致第 3 批首次启动失败。

这一问题确实干扰了调度节奏，但并不能解释“为何后续重试时发送内容改为简化版”。因此，线程上限属于本轮调度中的次要干扰因素，而不是本次上下文缺失事件的主因。

## 修复目标

本次修复工作的目标，不是对现象进行文字性补充，而是从机制上消除该类问题再次发生的条件。

需要实现的目标如下：

1. 所有 worldview 子代理派发，必须来源于已落盘、已验包的完整任务包
2. 后续批次、重试路径和异常恢复路径，必须与前两批共用同一套强约束分发链路
3. 一旦“已准备内容”与“待发送内容”不一致，整轮必须立即中止，不得继续运行
4. 监控和日志应能够自动识别“哪一批、哪个人格、在哪一步绕过了完整分发”
5. 即使主线程希望减少大段内容回显，也不得以牺牲子代理上下文完整性为代价

## 优化方案

### P0：建立发送内容强约束

#### 方案 1：在 `spawn_agent` 前增加最终一致性校验

在真正执行 `spawn_agent` 前，必须执行一次“待发送文本 = 已验包文本”的最终校验。如不一致，应立即失败并中止整轮。

该校验应满足以下要求：

- 不能仅校验 `packet.txt` 是否存在
- 不能仅校验 outgoing copy 是否已生成
- 必须直接校验“即将发送给子代理的文本”本身

#### 方案 2：禁止手写简化版派发

在 worldview panel 调度层增加明确约束：

- 不允许手写 `spawn_agent.message`
- 不允许以近似任务骨架替代完整任务包
- 不允许因后续批次、节省上下文或减少搬运而降级为简化版派发

如果无法做到这一点，则说明当前 dispatch 方案仍然不具备足够强的约束能力。

### P1：补齐测试与运行时识别能力

#### 方案 3：补充多批次与重试路径回归测试

建议至少新增以下测试场景：

- 在 24 个人格、4 个批次场景下，四批均必须携带完整材料
- 中途出现线程上限后，close/retry 之后仍必须携带完整材料
- 任意批次如缺少 `[人格底盘材料]`，应立即失败
- 当 `domain != other` 时，任意批次如缺少 `[当前领域材料]`，应立即失败

#### 方案 4：增强日志约束能力

目前日志能够记录批次开始和结果返回，但对协议偏离识别不足。建议增强如下：

- 每个批次、每个人格在 `spawn_agent` 前必须存在对应的 `dispatch_ready`
- 记录实际发送内容的长度和指纹
- 若某批次存在 `batch_start`，但缺少对应数量的逐人格验包记录，应直接判定为异常

### P2：改进流程与维护文档

#### 方案 5：区分“减少展示”与“减少发送”

本次事件本质上将两件事情混为一谈：

- 不希望继续在主线程中反复搬运大段任务包
- 最终却演变为后续子代理也不再接收完整任务包

后续流程应明确区分：

- 可以减少面向用户的回显和说明
- 不能减少发送给子代理的完整任务包

也就是说，可以减少展示，但不能减少发送。

#### 方案 6：补充维护 runbook

建议将本次事件沉淀为一份面向维护者的固定规则，至少明确以下内容：

- 何时必须重新验包
- 何时必须中止整轮
- 出现哪些日志组合，即可认定“实际发送内容”与“已准备内容”发生脱钩

这样后续排查不再依赖人工完整翻查调用链。

## 验收标准

本次问题修复完成后，至少应满足以下要求：

- 同一轮 24 个人格分 4 批执行时，四批均能获得完整任务包
- 中途 close/retry 后，不会退化为简化版派发
- 任何缺材料派发都能够被自动拦截，不会继续产出结果
- 不依赖用户人工翻查 session，也能通过日志或测试第一时间识别异常
